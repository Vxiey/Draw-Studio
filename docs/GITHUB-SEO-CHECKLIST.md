# GitHub SEO and discovery checklist for Image Draw Bot

Use this checklist when editing the repository About box, topics, README, release notes or public launch posts.

## Recommended GitHub About description

Use this as the repository description:

```text
Windows AutoDraw and drawing bot for Microsoft Paint, Gartic Phone and Skribbl.io. Converts images into smart mouse strokes, fills, contours and pixel-accurate drawings.
```

It front-loads the product category and the three strongest target-app search terms without repeating every feature.

Why these topics:

- `autodraw`, `auto-draw`, `autodrawer`, `drawbot`, `drawing-bot` and `drawingbot` match common naming used by similar GitHub projects.
- `microsoft-paint`, `gartic-phone`, `garticphone`, `skribbl` and `skribbl-io` capture target-specific searches.
- `mouse-automation`, `desktop-automation`, `windows`, `python` and `automation` place the project in broader technical discovery categories.
- `image-drawing`, `image-processing` and `drawing-app` describe the actual product purpose without inventing capabilities.

## README SEO rules

The first screen of `README.md` should answer three questions immediately: what is it, where does it run, and what can it draw into?

- H1: product name plus `AutoDraw` / `Drawing Bot` / `Windows`.
- First image: real application screenshot with descriptive alt text mentioning the target apps.
- First paragraph: naturally include Microsoft Paint, Gartic Phone, Skribbl.io, mouse strokes, fills and contours.
- Keep the Windows download section near the top.
- Add a single clear Star CTA after explaining the value.
- Use target-specific headings such as `Microsoft Paint AutoDraw quick start` and `Gartic Phone and Skribbl.io drawing-bot quick start`.
- Use keywords naturally; do not add a giant raw keyword list to the public README.
- Keep technical limitations and unsigned-build warnings accurate.

## GitHub discovery signals

GitHub exposes repositories through Search, Explore and topic pages. To improve legitimate discoverability:

- Keep repository topics complete and relevant.
- Maintain a clear README and working download path.
- Publish meaningful releases instead of noisy version bumps.
- Encourage real users to star the repository after they understand the project.
- Keep Issues and Discussions usable so people can interact with the project.
- Respond to reports and contributions; active repositories are easier for users to trust and share.

Do not buy, trade or automate stars. Stars are most useful when they come from people who actually want to revisit or follow the project.

## Distribution checklist

For meaningful releases, share a real screenshot or drawing result with a direct repository link. Good channels depend on each community's rules, but useful launch formats include:

- Reddit posts in relevant Python, Windows automation, drawing/game-tool or open-source communities where self-promotion is allowed.
- Hacker News `Show HN` for substantial releases.
- Relevant Discord communities where project sharing is permitted.
- GitHub Discussions and release announcements for existing users.

Use the ready-to-edit copy in [`docs/PROMOTION.md`](PROMOTION.md).

## Social preview

GitHub's Social preview is a repository setting and is separate from the README image. Use a clear real application screenshot or project artwork that remains readable when reduced to a link card.

Repository files are not automatically selected as the social preview. Upload the chosen image manually in **Settings → General → Social preview**.

## Release SEO rules

Release notes should start with a short plain-English summary of what Image Draw Bot does and then explain the specific improvement in that release. Use concrete product terms where they are actually relevant:

- Windows installer
- portable Windows ZIP
- Microsoft Paint automation
- Gartic Phone drawing bot
- Skribbl.io drawing bot
- image-to-strokes rendering
- Fill / contours / adaptive brush sizes
- Pixel Accurate mode
- exact RGB color calibration

Do not copy an identical keyword paragraph into every release; describe the actual change.

- `.github/ISSUE_TEMPLATE/feature_request.yml`
- `.github/pull_request_template.md`

## Avoid

- old product names in current branding
- keyword stuffing
- fake/downloaded/bought stars or vote exchanges
- unsupported claims about speed or compatibility
- claiming builds are signed while releases are unsigned
- claiming every Paint/browser layout is verified
- calling Actions artifacts official releases
- saying the app generates AI images when it performs deterministic local rendering
- calling the repository open-source unless an appropriate license file has actually been added
